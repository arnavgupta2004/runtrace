# RunTrace

**Local-first ML experiment comparison and reproducibility auditing**

RunTrace is a browser-only web application that lets you compare ML experiment runs side-by-side and audit reproducibility evidence — without sending your experiment artifacts to any external service.

---

## What it does

When ML experiments multiply, keeping track of which run used which dataset, which seed, and which code state becomes difficult. RunTrace solves this by:

1. **Parsing experiment artifact ZIPs in your browser** — metrics, configs, dependency lists, and git metadata.
2. **Ranking runs** by the metric you choose, with an explicit optimization direction (maximize or minimize).
3. **Detecting dataset/split mismatches** — flags when runs being compared used different datasets or evaluation splits, so you are not misled by an invalid comparison.
4. **Auditing five reproducibility dimensions** per run: git revision, random seeds, dataset identifiers, evaluation splits, and dependency versions.
5. **Exporting Markdown and JSON reports** generated entirely in your browser.

Nothing ever leaves the browser. No accounts, no backend, no telemetry.

---

## Primary workflow

1. Open the app.
2. Drop one or more experiment ZIP files onto the upload zone, or click **Load demo experiments** to try the built-in synthetic examples.
3. Select a metric and optimization direction (maximize / minimize) in the Metric comparison panel.
4. Read the comparison table and chart.
5. Inspect the dataset/split compatibility status.
6. Open each run's reproducibility audit to review evidence.
7. Click **Export Markdown** or **Export JSON** to download a report.

## Supported archive formats

RunTrace parses the following file types inside a ZIP. Only these formats are actively tested; any unrecognised file is recorded in the artifact index for evidence purposes only.

### Metrics files

| File pattern | Format |
|---|---|
| `metrics.csv` | CSV with header row; last value of each column used |
| `metrics.json` | Flat JSON object `{"metric": value}` or `{"metric": [values]}` (last value used) |
| `results.json`, `results_*.json` | Same flat-object format as `metrics.json` |

Non-finite metric values (`NaN`, `Infinity`, `-Infinity`) are excluded at parse time. Runs with no valid value for the selected metric are ranked last.

### Configuration files

| File pattern | Format |
|---|---|
| `config.yaml`, `config.yml` | YAML key-value |
| `params.yaml`, `params.yml` | YAML key-value |
| `hparams.yaml`, `hparams.yml` | YAML key-value |
| `config.json` | JSON object |

### Dependency files

| File pattern | Format |
|---|---|
| `requirements.txt` | pip format: `name==version` lines |
| `environment.yml`, `environment.yaml` | conda format: `dependencies:` list |

### Git metadata

| File | Keys parsed |
|---|---|
| `git_info.json` | `revision`, `commit`, `sha`, `dirty`, `is_dirty` |
| Any config file | `git_revision`, `commit`, `git.revision`, `git.commit` |

### MLflow local file store

RunTrace attempts to parse the MLflow local artifact directory layout when a ZIP contains it (`mlruns/<exp_id>/<run_id>/`). **Only ZIPs with exactly one MLflow run ID are supported.** Multi-run MLflow ZIPs return an error.

## ZIP size and entry limits

| Limit | Value |
|---|---|
| Maximum compressed size | 200 MB |
| Maximum entries | 5 000 files |
| Maximum total uncompressed size | 500 MB |

Files that would exceed the uncompressed-size limit are skipped with a warning.

## Config key mapping

The config parser recognises the following keys (case-insensitive):

| Config key(s) | Maps to |
|---|---|
| `seed`, `random_seed`, `data_seed`, `numpy_seed`, `torch_seed` | `randomSeeds` |
| `dataset`, `dataset_name`, `data_path`, `data_dir`, `dataset_version`, `dataset_id` | `datasetIdentifiers` |
| `eval_split`, `test_split`, `val_split`, `evaluation_split` | `evalSplits` |
| `git_revision`, `commit`, `git.commit`, `git.revision` | `gitRevision` |

## Comparison compatibility states

| State | Meaning |
|---|---|
| **Compatible** | All runs report the same dataset identifiers and evaluation splits (or none report any — handled as unverified by the auditor). |
| **Mismatch** | At least one run's dataset or split name differs from another's. Metric comparisons across these runs may not be scientifically valid. |
| **Unverified** | At least one run has no dataset or split metadata at all. Compatibility cannot be confirmed or denied. |

A mismatch warning is non-blocking. You can still compare metrics and see rankings; the warning reminds you that the comparison may not be meaningful.

---

## Five audit dimensions

RunTrace audits each run across five dimensions:

| Dimension | What is checked |
|---|---|
| **Git Revision** | Whether a commit hash was recorded. If `gitDirty: true`, the run is flagged as a "problem" — uncommitted modifications mean the hash alone does not fully describe the code state. |
| **Random Seeds** | Whether one or more named seeds were recorded (e.g. `seed`, `numpy_seed`, `torch_seed`). |
| **Dataset Identifiers** | Whether a dataset name or reference was recorded in the config. |
| **Evaluation Splits** | Whether an evaluation split name was recorded. |
| **Dependency Versions** | Whether a requirements.txt or environment.yml was included, and whether dependencies have pinned versions. |

### Audit scores

| Score | Meaning |
|---|---|
| **Good** | All five dimensions have confirmed evidence. |
| **Partial** | No problems found, but at least one dimension is missing evidence. |
| **Poor** | At least one dimension reports a known reproducibility risk (e.g. dirty git). |

**These scores are rule-based descriptive labels, not statistical reproducibility probabilities.** A "good" score means all five metadata dimensions were captured — it does not certify that the experiment can be reproduced.

## Markdown and JSON exports

When at least one run is successfully parsed and a metric is selected, the **Export Markdown** and **Export JSON** buttons become active.

Each export includes:
- The comparison result (metric, direction, ranking with deltas, and compatibility assessment).
- The full reproducibility audit for each run.
- A limitations section clarifying what the scores and statuses do and do not mean.

Exports are generated entirely in the browser using `Blob` and `URL.createObjectURL`. Filenames follow the pattern `runtrace-report-YYYY-MM-DD.md` / `.json`. No data is sent to any server.

---

## Privacy model

- All ZIP parsing, comparison, auditing, and export runs client-side.
- No experiment data, metrics, or metadata is transmitted to any server.
- No analytics, tracking, or telemetry is present.
- The application requires no account, authentication, or network connection after initial page load.

## Synthetic demo experiments

Three synthetic demonstration archives are included in `public/samples/`:

| Archive | Purpose |
|---|---|
| `baseline-experiment.zip` | A well-documented baseline with all five reproducibility dimensions recorded and a clean git state. |
| `improved-experiment.zip` | A follow-up run with the same dataset and evaluation split but different seed and better metrics. Compatible with the baseline for comparison. |
| `reproducibility-warning.zip` | Uses a different dataset and evaluation split (triggers a mismatch warning) and a dirty git working tree (triggers a "poor" audit score). Intended to demonstrate the warning states. |

**These are not real research data.** They are synthetic fixtures designed to exercise the parser, comparator, auditor, and exporter.

Click **Load demo experiments** in the upload section to load all three. Remove individual runs using the ✕ button on each card.

## Known limitations

- **Weights & Biases:** W&B formats are not supported. W&B run data is only accessible via the W&B API, which is out of scope.
- **MLflow:** Only flat-file (local artifact directory) format is supported. MLflow server / tracking server formats are not parsed. Multi-run ZIPs (more than one `run_id` under `mlruns/`) return an error.
- **Large ZIPs:** Parsing runs on the main thread (JSZip async, non-blocking but still CPU-bound). Very large ZIPs may cause a noticeable pause. The 200 MB compressed / 500 MB uncompressed limit is a guard.
- **Evidence is not verified:** Recording a git revision does not verify that the code at that commit is the code that was run. Recorded metadata confirms presence, not authenticity.
- **Comparison is not scientific proof:** A "compatible" status and a higher metric value do not establish that one model is scientifically superior to another.

## Static deployment

### Vercel (recommended)

1. Push the repository to GitHub.
2. Import the project at [vercel.com](https://vercel.com).
3. Vercel auto-detects Next.js and runs `npm run build`. The `output: "export"` setting in `next.config.ts` produces a static site.
4. The `public/samples/` directory is included in the output automatically.

### Any static host

After `npm run build`, deploy the contents of the `out/` directory to any static host (Netlify, GitHub Pages, S3 + CloudFront, etc.).

No server-side APIs, server actions, or image optimization routes are used. The deployment is fully static.

## Running the test suite

```bash
npm test          # run all tests once
npm run test:watch  # watch mode
```

Test files are in `__tests__/`. The suite covers:
- Parser: CSV/JSON metrics, YAML/JSON configs, requirements.txt, conda env.yml, git_info.json, MLflow layout, sample archives.
- Comparator: ranking, ties, deltas, compatibility assessment.
- Auditor: all five dimension checks, edge cases, dirty git.
- Exporter: Markdown and JSON formatting, escaping, non-finite values.
- Components: all UI components including upload, comparison, audit, export, and demo loader.
